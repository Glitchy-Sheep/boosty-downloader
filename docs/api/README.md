# Boosty API as the client sees it

`boosty-api.yaml` is an OpenAPI 3.1 document built from live answers of the Boosty API. Boosty publishes no specification; this file is the observed one: it says which keys the three endpoints the client calls have returned, of which types, how often, and which values the vocabulary fields (`type`, `uploadStatus`, ...) took. It is regenerated by hand and reviewed like code.

## Regenerate

```bash
task api:schema -- <blog> [<blog> ...]
```

Blog metadata (`GET /blog/{blog}`), one listing page (100 posts) per blog and the newest post through the single-post endpoint. The account token is sent when one is found, in this order: `BOOSTY_TOKEN` in the environment, `auth.auth_header` of `config.yaml` (`--config PATH` points elsewhere), `BOOSTY_TOKEN` in `./.env`. With it, locked posts of the blogs the account can read show their shape, and the blogs are read a second time without it: a stranger gets different answers (`price` in USD instead of RUB, no `views`), and the canary reads as a stranger. `--anonymous` after `--` sends no token; `--pages N` reads more pages per blog.

The file records counts only. Blog names, post ids, titles, texts and links never land in it: strings are dropped, except short token-like values of vocabulary keys. The test tree has the same rule for its own data (`test/unit/synthetic_data`).

## Reading the file

- `x-observed`: capture date and sample counts for the post endpoints. Its `blog_info` section records the date and blog/view/response counts for blog metadata. The dates may differ when only one endpoint is refreshed; retained components keep their original capture metadata.
- `required`: keys present in every sampled object. Anything else carries `x-presence`, the share of samples that had it. `subscriptionLevel` at 0.4 means only locked posts carry it.
- `type: [string, 'null']`: a null was seen at least once. A strict model must allow it.
- `Chunk*` components describe `data[].type` in posts; `BlogDescriptionChunk*` describe `description[].type` in blog metadata. Each kind has its own component, chosen by `discriminator`. The two groups keep their own observed fields and frequencies. A chunk kind that appears in answers and has no component here is new.
- `enum`: a closed list the client switches on (video qualities). A value outside it is drift.
- `x-seen-values`: the values a vocabulary field took, for reading. A new one is information, not an error.
- `x-unread-by-client`: keys the client's pydantic models do not read. The list of what Boosty sends and the app ignores.

## What changed since

```bash
task api:changes -- <blog> [<blog> ...]
```

Reads the blogs the same way and writes to `api-changes.json` what the answers have and this file lacks: new chunk kinds, keys, types and vocabulary values. Keys missing from the answers are not listed: one page rarely holds every key. The weekly canary runs it anonymously and the weekly report shows the result. Regenerating the file accepts the changes.

## Limits

The schema is statistics over a sample. A key absent from the sampled posts is absent from the file; a key present in every sampled post is `required` even if Boosty treats it as optional. More blogs and more pages make it closer to the truth; a diff against the previous file shows what the new sample added.
