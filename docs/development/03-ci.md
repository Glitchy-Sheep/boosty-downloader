# CI Pipeline

Workflow: `.github/workflows/ci.yaml`. Runs on pull requests targeting `main` or `feat/v5`, and on pushes to either branch.

## Steps

| Step | Command |
|------|---------|
| Lint | `task check:lint` |
| Format | `task check:format` |
| Types | `task check:types` |
| Layers | `task check:imports` |
| Unit and e2e tests | `task test:cov -- -v` |
| Integration tests | `task test:api -- -v` (skipped if `.env` is missing) |
| Viewer API type freshness | `task ui:types` + tracked-file and Git diff checks |
| Viewer types, lint and unit tests | `task ui:check` |
| Viewer assets | `task ui:build` |
| Viewer browser tests | `npm run e2e` in `viewer-ui/` after building assets |
| Changelog | Custom diff-based check |
| Build | `task build` + artifact verification |

To reproduce locally: run `task ui:types` to refresh API declarations, `git diff --exit-code -- viewer-ui/src/lib/api.gen.ts` to check them against the index, then `task ci` for Python and UI checks, unit tests and the complete package build. Run `task ui:e2e` separately for browser tests after installing the Playwright browsers as described in [Dev Tools](01-dev-tools.md). Node 24 is required. The build job installs Node from `.nvmrc`, installs the npm lockfile, builds the UI and includes it in both distributions. Artifact verification checks the HTML entry point, JavaScript/CSS, their Brotli/gzip companions and the existing Jinja templates. Python lint and test jobs do not install Node; editable Python setup does not require built UI assets.

The independent `ui` job installs the pinned Python environment and Task through the shared setup action, then Node from `.nvmrc`. It verifies that `api.gen.ts` is tracked and present, regenerates it from Python API models with `task ui:types` at the repository root, and rejects a Git diff. It then checks TypeScript, oxlint, Vitest and the production frontend build from `viewer-ui/`. Playwright runs Chromium and Firefox against a temporary synthetic library served by the real CLI. Browser checks cover authors, storage, the virtual post timeline, URL filters and navigation, responsive layout, themes, accessibility and API error recovery. Reports, screenshots and failure traces are uploaded as `viewer-browser-results` for seven days. This job fails independently when declarations are stale or frontend checks fail, even if Python tests pass.

## Test matrix

The test job runs four times, one job per cell:

| OS | Python | Why |
|----|--------|-----|
| Ubuntu | 3.10 | the oldest version `requires-python` allows |
| Ubuntu | 3.12 | the pin in `.python-version`, same as local development |
| Ubuntu | 3.14 | the newest supported version |
| Windows | 3.12 | paths, line endings and the console differ from Linux |

Lint, types and the build run on the pinned Python on Ubuntu only. The cells are independent (`fail-fast: false`): one red cell does not cancel the others, so a PR shows every failing combination at once.

The setup action takes the Python version as an input and hands it to `astral-sh/setup-uv`, which exports `UV_PYTHON`. That variable wins over `.python-version`, so `uv sync` installs and uses the requested Python. Without the input the pin applies.

To run the suite on another Python locally without touching `.venv`:

```bash
UV_PROJECT_ENVIRONMENT=/tmp/venv310 uv run --python 3.10 --isolated pytest test/unit/ test/e2e/
```

## Canary: the live Boosty API

Workflow: `.github/workflows/canary.yaml`. Runs every Saturday at 06:00 UTC, three hours before the weekly report, and on demand from the Actions tab.

The job reads the public blog named by the `CANARY_AUTHOR` repository variable, no credentials, and sorts what it sees into two levels.

**Breaking: an issue.** `task test:canary` checks what the app needs today:

- every post on the page parses
- at least one open post carries content; otherwise the first check proves nothing

**New: a warning.** `task api:changes` compares the answers with `docs/api/boosty-api.yaml` and lists what the schema lacks: a new chunk kind, key, type or vocabulary value. Nothing fails on it. The list goes to the `api-changes` artifact, and the weekly Telegram report shows it in the 🔭 API changes block. To accept the changes, regenerate the schema with `task api:schema` and commit it; they stop showing up.

A manual run can name another blog through the `author` input.

When the probe fails, the workflow opens an issue with the `api-drift` label and a link to the run. While such an issue is open, later failures add nothing. A failed setup (empty `CANARY_AUTHOR`, a broken install) does not open an issue.

Locally: `CANARY_AUTHOR=<blog> task test:canary`.

## Changelog Enforcement

CI verifies that **new lines were added** to the `## Unreleased` section - not just that the file was touched.

### Algorithm

1. Checks that `## Unreleased` heading exists in the file
2. Extracts the Unreleased section from both the base branch and the PR branch
3. Diffs the two sections and looks for added lines
4. Passes only if there are new non-empty lines

On success, the added entries are printed in the CI log and written to the GitHub Actions **job summary** (visible in the PR's "Summary" tab).

### Skipping

Add `[skip changelog]` to the **PR title** or the `ci/skip-changelog` **label**.

## Caching

The uv package cache is keyed by the `uv.lock` hash, the OS and the Python version (built into `astral-sh/setup-uv`), so every matrix cell keeps a cache of its own. `uv sync` then assembles `.venv` from that cache in seconds.

The viewer and build jobs cache npm downloads using `viewer-ui/package-lock.json` as the dependency key. They still run `npm ci`; `node_modules` is not reused between jobs.

The viewer job also caches Playwright browser binaries by OS and npm lockfile. The browser installation step still runs on a cache hit to ensure the expected binaries and system libraries are available.
